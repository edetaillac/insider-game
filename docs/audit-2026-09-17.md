# Audit insider-game

## TL;DR

Le jeu fonctionne encore (il démarre sur Node 22) mais il n'est pas viable en l'état pour trois raisons.

1. Dépendances de 2017-2020 : 22 vulnérabilités connues dont 4 critiques (ejs 1.0.0 RCE, socket.io 1.7.4). La montée socket.io 1 → 4 est cassante côté client
2. Le serveur diffuse les secrets à tout le monde : rôles de tous les joueurs et mot à deviner partent en broadcast, le client filtre. Tricher se fait dans l'onglet réseau des devtools. Aucune vérification d'identité ni de permission côté serveur
3. L'état de l'UI a deux sources de vérité (jQuery qui toggle des div, et EJS qui rend depuis `game.status`). Un rechargement en cours de partie ou en fin de partie donne un écran vide

Le code est petit (357 lignes serveur, 330 lignes client, 45 fichiers). Un refacto profond et une réécriture coûtent à peu près la même chose. Recommandation : ne pas retoucher l'existant au-delà d'un P0 de sécurisation, et reconstruire autour d'un moteur de jeu pur et testé, avec un contrat "snapshot d'état" entre serveur et client. Le front se refait en dernier, une fois ce contrat posé.

## Périmètre observé

| Élément | Constat |
|---|---|
| Stack | Node, Express 4.17, socket.io 1.7.4, EJS 1.0.0, jQuery 1.10.2 et Bootstrap 4.0.0 via CDN |
| Taille | `app.js` 357 lignes, `board.ejs` 328 lignes (dont ~230 de JS inline), 3 vues, 2 CSS |
| Données | Une liste de 855 mots en CSV, état de jeu en mémoire process, une seule partie globale |
| Tests / lint / CI | Aucun |
| Docker | Dockerfile simple, compose avec volumes de dev, pas de `.dockerignore` |
| Historique | 29 commits du 16/04 au 09/05/2020, projet confinement |

## Constats

### 1. Sécurité et dépendances

Audit npm sur le lockfile : 22 vulnérabilités, 4 critiques, 11 hautes, 2 modérées, 5 basses.

- ejs 1.0.0 : injection de template et RCE. Version courante 3.x
- socket.io 1.7.4 (2017) et toute sa chaîne (engine.io, socket.io-parser, ws, xmlhttprequest-ssl) : DoS, CORS, injection de code. Version courante 4.x, API client et serveur ont changé (`io.listen` retiré, `socket.join` synchrone, options CORS explicites)
- express 4.17.1, body-parser 1.19, qs, path-to-regexp : ReDoS, open redirect, prototype pollution. body-parser est intégré à Express depuis la 4.16, la dépendance est inutile
- `ent` est déclaré mais jamais utilisé
- Secret de session en dur dans le code (`app.js:34`), pas de `resave` ni `saveUninitialized` (warnings au boot), port 8080 en dur (`app.js:357`)
- Front chargé depuis 3 CDN sans épingle ni intégrité pour jQuery et Font Awesome. jQuery 1.10.2 date de 2013

### 2. Modèle de confiance inexistant

C'est le point le plus structurant, plus que les CVE.

- `newRole` (`app.js:281`) et `revealWord` (`app.js:286`) émettent à toute la room la liste complète des joueurs avec leurs rôles, plus le mot. Chaque client reçoit le rôle du traître et le mot, et se contente de ne pas l'afficher
- Les votes portent le nom du joueur envoyé par le client (`board.ejs:207`, `:213`). N'importe qui peut voter à la place de n'importe qui, ou voter deux fois
- Les actions admin (`resetGame`, `startGame`, `displayVote1`, `displayVote2`, `revealWord`) sont acceptées de n'importe quel socket. Le rôle admin n'existe que dans le template
- `/adminPlayer`, `/addPlayer`, `/deletePlayer` (un GET qui mute) et `/setWord` sont ouverts à tous
- Aucun lien serveur entre un socket et un joueur : la session Express n'est pas partagée avec socket.io

Conséquence : impossible de rendre le jeu robuste par correctifs locaux. Il faut que le serveur sache qui est derrière chaque socket et n'envoie à chacun que ce qu'il a le droit de voir.

### 3. Bugs de logique

- `/game` (`app.js:82-90`) : pas de `return` après le redirect quand la session est vide, le code continue, `me[0]` est `undefined`, le rendu plante et Express logge "Cannot set headers after they are sent"
- `comparePlayer` (`app.js:125`) n'est pas un comparateur valide (retourne 0 quand `a > b`, jamais de positif). Le tri est indéfini. Le dernier commit "Fix Player order with final Vote" témoigne du combat
- `processVote2Result` (`app.js:246`) lit `votePlayers[1]` sans garde : plante à 2 joueurs
- `nbVote2` n'est remis à zéro que dans `resetGame`, pas dans `resetVote(2)`. Un second `displayVote2` sur la même partie double les compteurs
- Compteur `online` : incrémente sur `newPlayer`, décrémente sur tout `disconnect`. Deux onglets comptent double, `offline` peut passer négatif
- Le mot est lu par `split("\r\n")` : le fichier est en CRLF aujourd'hui, une sauvegarde en LF transforme les 855 mots en un seul
- Le socket client cible `localhost:8080` en dur (`board.ejs:102`). Chaque joueur distant se connecte à sa propre machine. Le jeu distant ne marchait qu'avec une modification locale non versionnée (le `.gitignore` liste un `docker-compose.override.yml`)
- Variables globales implicites partout (`game`, `me`, `ghostPlayer`, `voteResult`, `votePlayers`, `hasWon`, `humanPlayers`, `offline`, `seconds` dans `timer.js`). Ça tient parce que le fichier n'est pas en mode strict. Un ESLint le signalerait en une passe
- `game` est initialisé paresseusement dans un middleware HTTP. Un événement socket avant la première requête HTTP planterait
- Deux joueurs en dur au démarrage (Hélène, Manu)

### 4. UI et machine d'états

- L'enchaînement des écrans vit dans le client : chaque événement socket fait `$('.hidden').hide()` puis `fadeIn` d'une div. Le serveur porte un `status` parallèle, rendu par EJS au chargement. Les deux dérivent
- Les statuts `in_progress` et `end` ne sont pas gérés par `board.ejs`. `resultVote2` est passé à la vue et jamais utilisé. Rechargement pendant le chrono : message d'attente jusqu'au tick suivant. Rechargement en fin de partie : écran vide
- Une seule partie globale par serveur, pas de notion de room ni de code de partie. L'enrôlement passe par une page admin où on pré-saisit les prénoms
- Règle officielle absente : si le mot n'est pas trouvé avant la fin du chrono, tout le monde perd. Ici le chrono à zéro joue un son et rien d'autre
- Sons déclenchés par événements socket sans geste utilisateur : bloqués par la politique autoplay de Safari iOS et Chrome, promesse `play()` non gérée. Pour un jeu pensé pour le téléphone, c'est visible
- `nosleep.min.js` est présent mais jamais chargé (fichier mort). `user-scalable=no` dans le viewport
- XSS : mot personnalisé et noms de joueurs injectés via `.html()` sans échappement (`board.ejs:147`, `:253`, `:303`)

### 5. Outillage et exploitation

- Pas de tests alors que la logique de jeu (rôles, mélange, votes, résultat) est pure et petite : le meilleur ratio effort / valeur du repo
- Pas de lint, pas de CI, pas de `.nvmrc` ni de champ `engines`
- Dockerfile : `node:lts-alpine` non épinglé, `npm install` au lieu de `npm ci`, exécution en root, `COPY . .` embarque screenshots et PDF, pas de `.dockerignore`
- `docker-compose.yml` : clé `version` obsolète, volumes de dev montés sans rechargement à chaud (il faut redémarrer le conteneur à chaque édition de `app.js`)
- `package.json` : nom `concept-boardgame` (copié d'un autre projet), auteur avec une entité HTML `&gt;`
- HTTP seul, aucune configuration par variables d'environnement

## Ce qui ne se ferait plus comme ça aujourd'hui

- Diffuser tout l'état à tous et filtrer côté client. Aujourd'hui : émission ciblée par socket (`io.to(socketId)`) ou une room par joueur, à partir d'une identité vérifiée côté serveur
- Piloter l'UI par une cascade de `hide()` / `fadeIn()`. Aujourd'hui : le serveur envoie un snapshot d'état personnalisé (phase, mon rôle, ce que je peux faire), le client le rend intégralement à chaque réception. Le rechargement devient gratuit
- Une partie unique par process. Aujourd'hui : rooms avec code à 4 lettres, pseudo libre, l'hôte de la room a les droits d'admin
- Express + EJS + jQuery inline. Aujourd'hui : TypeScript, ESM, socket.io 4, et un client léger (Svelte + Vite, ou vanilla avec une fonction `render(state)`). Express reste défendable pour servir deux pages, Fastify ou Hono aussi, le choix est secondaire
- Logique de jeu mêlée aux handlers socket. Aujourd'hui : un module `engine` pur (état in → état out), testé avec `node:test` ou Vitest, et une couche transport fine
- CDN non épinglés. Aujourd'hui : dépendances front bundlées par Vite, ou à défaut CDN épinglé avec `integrity`
- Node LTS flottant en root. Aujourd'hui : image épinglée, multi-stage, `npm ci --omit=dev`, utilisateur non root, `.dockerignore`, healthcheck

## Priorités

### P0, remise en état sans toucher au design (1 soirée)

Objectif : pouvoir relancer une partie sans honte, et poser les filets avant le refacto.

1. Monter les dépendances : socket.io 4, express 4.21 (ou 5), ejs 3, retirer body-parser et ent. Adapter les trois points cassants (`io.listen`, `io.connect`, options)
2. Remplacer `io.connect('localhost:8080')` par `io()`
3. Ajouter le `return` manquant dans `/game`, sortir secret et port en variables d'environnement
4. ESLint avec `no-undef` et `'use strict'` ou passage en ESM : élimine les globales implicites
5. Dockerfile épinglé sur `node:22-alpine`, `npm ci`, `.dockerignore`, champ `engines`
6. Échapper le HTML injecté côté client (3 endroits)

Ce P0 ne corrige pas le modèle de confiance ni la double source de vérité. Il rend le repo sain pour travailler.

### P1, le vrai refacto (3 à 5 soirées)

Séquence recommandée, chaque étape laisse le jeu jouable.

1. Extraire un module `engine` pur : `createGame`, `assignRoles`, `castVote1`, `castVote2`, `resolve`. Tests unitaires d'abord, en reproduisant les bugs connus (comparateur, 2 joueurs, `nbVote2`). C'est là que le comportement du jeu se fige
2. Machine d'états explicite côté serveur : `lobby → roles → word → playing → vote1 → vote2 → end`, transitions validées (qui a le droit, depuis quelle phase). Ajout de la règle "chrono écoulé, tout le monde perd"
3. Identité : lier session et socket (middleware partagé ou token émis au join), stocker `socketId` par joueur. Toute action lit l'identité côté serveur, plus jamais dans le payload
4. Snapshot personnalisé : à chaque transition, le serveur calcule pour chaque joueur une vue (phase, son rôle, le mot s'il y a droit, ses actions possibles, résultats publics) et l'émet à son socket. Le client passe à un `render(state)` unique. Les vues EJS peuvent rester à ce stade, le JS inline est remplacé
5. Rooms : `Map<code, Game>`, join par code + pseudo, hôte = admin. La page admin disparaît

### P2, produit et front (à cadrer après P1)

- Refonte du client : sortir jQuery et Bootstrap 4, Svelte + Vite ou vanilla + CSS moderne, mobile first, déblocage audio au premier geste, écran qui reste allumé (Wake Lock API plutôt que nosleep.js)
- Timer configurable, plusieurs listes de mots, historique de parties dans la room
- Déploiement simple avec websockets (Fly.io, Railway, ou un Raspberry à la maison), HTTPS
- PWA installable

## Options de trajectoire

### Option A, refacto incrémental (garder Express, EJS, l'arborescence)

- Feasibility : haute, le code est petit et lisible
- Complexity : moyenne, le piège est de garder le JS inline de `board.ejs` comme point d'entrée et de retomber dans le toggle de div
- Risks : refaire un P1 partiel et garder la double source de vérité. Rester en JS sans typage sur un contrat serveur / client qui va grossir
- Recommendations : viable si l'ambition est "rejouer entre amis cet hiver" sans aller plus loin

### Option B, reconstruction autour d'un moteur testé (TypeScript, socket.io 4, client léger)

- Feasibility : haute, ~700 lignes à réécrire, règles connues et documentées par les screenshots et le PDF de règles
- Complexity : moyenne, le contrat de snapshot demande de la rigueur mais le domaine est minuscule
- Risks : dérive de scope (rooms, PWA, design) avant d'avoir un jeu jouable. Le garde-fou est la séquence P1 où chaque étape reste jouable
- Recommendations : c'est l'option recommandée. Le surcoût par rapport à A est faible et c'est la seule qui règle le modèle de confiance et la machine d'états proprement

## Points ouverts à trancher

- Ambition : rejouer en famille (A suffit) ou en faire un petit produit ouvert à d'autres groupes (B et rooms obligatoires)
- Le front : garder un rendu serveur minimal ou partir sur Svelte. Décision à prendre après P1 étape 4, une fois le snapshot posé, pas avant
- Hébergement : local sur le réseau (comme en 2020) ou exposé sur Internet. Ça conditionne HTTPS, l'authentification de room et le sérieux du P0 sécurité
